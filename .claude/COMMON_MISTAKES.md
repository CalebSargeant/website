# Common mistakes

Things that go wrong in this stack. Symptom, cause, fix.

## Build

- **A template typo fails the whole build instead of rendering nothing.** `scripts/build.py` runs Jinja with `undefined=StrictUndefined`. `{{ profile.emial }}` is a `UndefinedError` with a line number, not an empty string. That is the point: a CV with a silently blank field is worse than a red build. Check the name against `docs/template-context.md`, which is the full list of what a template is given.
- **Your edit to a page had no effect.** You edited `dist/`. It is deleted at the start of every build (`shutil.rmtree(OUT)`), it is gitignored, and it is only ever output. The layout is in `templates/`, the words are in `data/`.
- **`TemplateNotFound` after adding a page.** `PAGES` in `scripts/build.py` is the list of pages; the template it names has to exist. The same entry drives the nav (`nav:`), the sitemap (`sitemap: False` to omit) and the `<title>`/`<meta description>`, so a page added anywhere else in the repo simply does not exist.
- **A date change explodes the build with `unparseable date`.** `parse_ym` accepts `YYYY-MM`, `YYYY`, a real YAML date, or `present`. `Jun 2025`, `2025/06` and `current` do not parse. Quote nothing and write `2025-06`.
- **A role's duties silently come out empty.** `duties_see:` is resolved with `by_id.get(...)`, so pointing it at an id that does not exist yields an empty list rather than an error. Check the spelling against the `id:` of the role you meant.

## PDFs

- **The PDF renders in Times or another fallback font.** Chromium reports `networkidle` once the font *files* have arrived, which is before it has swapped them in. `render_pdf.py` awaits `document.fonts.ready` after `goto` for exactly this reason. Anything new that prints a page needs the same await, or the first sheet reliably prints wrong.
- **Printing a sheet from a `file://` URL looks fine and is not.** The Google Fonts request is blocked as cross-origin and root-relative asset paths resolve against the filesystem root, so you get a fallback font and no CSS. `render_pdf.py` spins up a throwaway HTTP server on an ephemeral localhost port and prints from that. Do not "simplify" it back to `file://`.
- **`make pdf` fails with a browser error after a clean `pip install`.** Playwright's Chromium is a separate download: `python3 -m playwright install chromium`. `make install` does both steps.
- **The CV quietly grew to three pages.** Adding `highlights` to a role in `data/experience.yml`, or `cv: true` skills in `data/skills.yml`, or `featured: true` education/courses, all push the A4 CV sheet. `render_pdf.py` warns past the budget in `MAX_PAGES` (CV 2 pages, cover 1) but does **not** fail the build, so nobody sees it unless they read the output. Aim for about 18 `cv: true` skills and about six featured education entries.
- **Adding a role lengthens the JDs PDF automatically.** `duties:` only ever reach `/experience` and `Caleb_Sargeant_JDs_and_Duties.pdf`, which has no page limit and is meant to grow. The CV takes `highlights:` only. Putting the long-form duty list into `highlights` is what overflows the CV.
- **A committed PDF appears in a diff.** It should not exist. `dist/` is gitignored and CI rebuilds all three on every deploy, so a downloaded CV can never disagree with `data/`. The OG card and the favicons are the deliberate exception, generated by `scripts/render_images.py` and committed.

## CSS, JS, templates

- **A colour is right in one theme and wrong or invisible in the other.** Every token is declared on `:root` in `assets/site.css`; `:root[data-theme="light"]` redefines only the named subset in `docs/design-system.md` section 1. A colour defined *only* inside a theme block is undefined in the other theme. Declare it on `:root` and override it if it needs to change.
- **Content is invisible with JavaScript disabled.** `.reveal` must only hide when `<html>` carries `.js`, which the inline bootstrap adds. Any new "animate in" class needs the same gate, plus the 1600ms safety net that force-adds `.in`. The accessibility floor (design-system section 6) is that the site is fully readable and navigable with JS off.
- **Renaming a class breaks two files you did not open.** `docs/design-system.md` section 3 is the shared vocabulary of `assets/site.css`, `assets/site.js`, `assets/hero-net.js` and `templates/`. Class names, ids and `data-` attributes are the interface. Rename in the doc and all three, or not at all.
- **A page-specific `<script>` or `<link>` gets dropped.** Child templates put them in `{% block head %}` / `{% block scripts %}`. `base.html` owns `<head>`, the nav, the footer and the palette markup, and derives `<title>` and the meta description from `page`, so a child never sets them. The print templates deliberately do **not** extend `base.html`.

## Delivery

- **A new inline `<script>` does not run.** `_headers` sets the CSP. Today `script-src` still allows `'unsafe-inline'` with a TODO to pin the theme bootstrap by hash. Once that hash lands, browsers ignore `'unsafe-inline'` entirely and every other inline script is dead. Keep inline JS to that one pre-paint snippet.
- **The CSP vanishes from some responses.** Custom headers are not applied to responses generated by Worker code. `_headers` is authoritative only because `wrangler.toml` has no `main` entrypoint. Adding one silently strips the CSP from everything that entrypoint handles.
- **Deploy fails: `Hostname 'www.calebsargeant.com' already has externally managed DNS records`.** Cloudflare refuses to attach a Worker custom domain to a hostname that already has its own A or CNAME record, and Wrangler cannot force past it (the `override_existing_dns_record` option the error suggests is [not exposed by the CLI or config](https://github.com/cloudflare/workers-sdk/issues/9878)). Delete the stale record in the dashboard (DNS, then Records) and re-run; Wrangler creates the right one itself.
- **PR previews stop producing a URL.** `preview_urls` defaults to whatever `workers_dev` is, and `workers_dev = false` here to avoid a duplicate indexable copy of the site. The explicit `preview_urls = true` is what keeps previews working; check that line first. Also note `wrangler versions upload` uploads a version of an existing Worker, so `main` has to have deployed at least once.
- **Deploy fails with `Wrangler requires Node.js v22`.** Wrangler 4.x refuses older Node. The workflow pins `actions/setup-node`; do not remove it.
- **A print sheet turns up in search results.** `robots.txt` disallows `/print/` and those pages are `sitemap: False`. Keep both when adding a fourth sheet, or the sheet competes with the page it is a print copy of.

**Cloudflare deploy: assets upload, then "Some triggers failed to deploy"**
`wrangler deploy` uploads every asset and only then attaches the custom domain, so a
failure at `/workers/scripts/<name>/domains/records` means the site is uploaded but
unreachable on www. Wrangler swallows the API error body, so the log alone cannot tell
the two causes apart, which is why the workflow has an `Explain the deploy failure`
step that re-runs with `WRANGLER_LOG=debug`.
- The hostname already has its own DNS record. Cloudflare will not attach a Worker
  custom domain over one, and `override_existing_dns_record` is not exposed by the CLI.
  This is the case when the hostname is still serving whatever it served before, as
  www.calebsargeant.com did for the Google Sites version.
  **Deleting the record is not the only fix, and usually not the best one.** A plain
  Workers route binds to a hostname that already has a proxied record and intercepts
  the request before it reaches the origin, so the Worker serves and the old origin is
  never asked. That needs only `Workers Routes: Edit`, which the deploy token already
  has, and it has no cutover window. `wrangler.toml` here uses routes for exactly this
  reason. Reach for deleting the record only if you actually want the custom-domain
  API's cert and DNS provisioning.
- The API token lacks **Zone -> Workers Routes: Edit** for that zone. This, not
  `DNS: Edit`, is the permission that attaches a custom domain, and a token scoped to
  the account but to no zone (or to the wrong one) fails here and nowhere else.

**`/user/tokens/verify` returning 401 does not mean the token is bad**
It only works for user-owned API tokens. An account-owned token, which is what the
Workers deploy token is, returns `1000 Invalid API Token` there while working perfectly
everywhere else. Chasing that 401 cost a diagnostic cycle the first time. To judge a
deploy token, call something it is actually scoped for: `GET /zones?name=<zone>` and
`GET /zones/<id>/workers/routes`, which is what the workflow's probe does.

**Dependabot PRs cannot read repo secrets**
They run against GitHub's separate `dependabot` secrets context, so any job needing
`CLOUDFLARE_API_TOKEN` fails on every dependency bump. Guarding on
`github.event.pull_request.head.repo.full_name == github.repository` does not cover it,
because a Dependabot PR is not a fork. Skip on `github.actor != 'dependabot[bot]'` too.
